1. What the connector does

GLEIF is an inbound, read-only corporate-registry connector. It retrieves JSON:API legal-entity data and relationship records without credentials.

Validate an LEI

Retrieve one pinned legal-entity record by its 20-character LEI.

Find a company

Search by national registration identifier and authority, or fuzzy-match a legal name.

Build hierarchy

Follow direct-parent and ultimate-parent relationships using the subject LEI.

Governed enrichment

Map legal name, status, jurisdiction, addresses, identifiers, and parent data into approved EBX fields.

4. Build the mapping

GLEIF responses follow JSON:API. A single-record mapping reads from data.attributes; nested legal name, entity status, jurisdiction, headquarters/legal addresses, registration authority, and validation information must be mapped using the exact response paths.

Fixture LEI: 529900T8BM49AURSDO55
Expected response type: lei-records
Single-record attributes root: data.attributes
  1. Select the existing GLEIF connector and mapping.
  2. Calculate the LEI or registration inputs from the current EBX record.
  3. Use update policies that protect stewarded/high-trust values.
  4. Map repeating addresses or identifiers through approved child mappings.
  5. Simulate against a known existing company before any live enrichment.

5. Full and delta loads

Bounded full load

Specify filters, pages, records, and maximum API calls before execution. Reconcile requested, created, updated, skipped, and failed counts. An identical rerun must create no duplicate LEI records.

Delta load

Persist a successful watermark, query a bounded overlap window, and advance the watermark only after complete success. Restart and no-change reruns must be safe no-ops.

429, timeout, 5xx, malformed-response, and schema-evolution cases should be replayed with controlled fixtures. Label replay evidence explicitly; do not represent it as a live GLEIF response.

6. Safe operating sequence

  1. Run the read-only diagnostic against the public endpoint.
  2. Retrieve the pinned LEI and verify type=lei-records.
  3. Simulate the existing mapping and inspect every proposed field change.
  4. Execute against one existing EBX company; retain the run ID and metrics.
  5. Try an invalid LEI and require a recoverable no-data/not-found outcome with no EBX modification.
  6. For bulk modes, reconcile counts, rerun for idempotency, and validate watermark behavior.
