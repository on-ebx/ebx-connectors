1. What the connector does

The Kafka connector connects EBX mappings to Kafka topics. Outbound mappings publish one JSON document; inbound mappings preview or consume messages and map their fields into EBX records.

Outbound

Publish company or other governed records to a topic, optionally choosing a message key from the outbound document.

Inbound

Peek during design without committing, then consume in a bounded batch with consumer-group offsets.

Streaming controls

Configure group ID, offset reset, poll duration, message limit, envelope, acknowledgements, and security protocol.

Data Catalog

Inventory topics, infer fields, profile recent messages, and sample text values.

4. Map Kafka events

Outbound mapping

  1. Select publish and the destination topic.
  2. Map only the approved EBX fields to the JSON document.
  3. Choose a stable key when ordering or compaction semantics require it.
  4. Simulate and inspect the calculated JSON before delivery.

Inbound mapping

  1. Use peek while discovering fields and testing rules.
  2. Configure the import-feed item path, record key, create/update policy, and child collections.
  3. Switch the approved live mapping to consume.
  4. Keep the same consumer group across restarts to resume from its committed offset.

5. Safe operating sequence

  1. Run the connector diagnostic and confirm the expected broker/topic metadata.
  2. For outbound, publish one tagged record and read it independently from the topic.
  3. For inbound, preview with peek; verify that the consumer-group offset does not move.
  4. Run one bounded consume; verify EBX counts and that the committed offset is the one after the last message EBX wrote (it never moves past a message that failed).
  5. Restart EBX cleanly and confirm the group resumes at the same offset without duplication.
  6. Review connector health, duration, request/read/write/skip/error metrics, and the synchronization log.
Accepted behavior: the acceptance run published and independently read an outbound event, previewed without committing, consumed and committed, resumed after restart at lag zero, and recovered after malformed input.

6. Catalog and profiling

Use source as the catalog source identifier. Optional schemas and tables narrow topics; sampleSize and limit bound reads. Fields are inferred from recent JSON messages, so heterogeneous payloads and empty topics require deliberate review.

Catalog inference is evidence from sampled messages, not a broker-enforced schema. Use Schema Registry or governance controls when a stable contract is required.

7. Errors and recovery

SymptomCheck
No messagesTopic, group, committed offset, reset policy, poll time, and producer destination.
Duplicate processingStable group ID, offset commit result, record-key mapping, and EBX idempotency policy.
Malformed JSONThe message is reported in the run and never delivered. Without dead.letter.topic it is left uncommitted: its partition stays at that offset and the run says so on every pass; set the property to move such messages aside, or remove the message.
A partition does not advanceThe run's results say Partition p of t stays at offset o: the message at that offset failed in EBX or is not JSON. Fix the mapping or the data, or set dead.letter.topic.
Authentication failureSecurity protocol, SASL mechanism, encrypted credentials, truststore, and broker ACLs.
Large transactionReduce max.messages; review message size and mapping child collections.
