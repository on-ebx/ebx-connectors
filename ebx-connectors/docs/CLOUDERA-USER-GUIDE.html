Cloudera Hive and Impala

Read-only access to the Hive and Impala tables of a Cloudera platform, with a user name and a password over TLS.

Run against Apache Hive 4.0.1 with the Apache driver; never against Impala, Knox or a Cloudera platform
On this page1. Scope2. Configure3. Authentication4. Boundaries5. What is proven

1. Scope

Two connection types reuse the bounded JDBC engine: cloudera-hive (query, catalog, profile, sample) and cloudera-impala (query, catalog, sample). Both read tables into ON EBX and feed the catalogue scan. Neither writes.

Files (HDFS through a Knox or HttpFS gateway) are the Hadoop WebHDFS / HttpFS connection; an Ozone bucket is reached with the S3 connection and its endpoint property; Kafka with the Kafka connection.

No driver is packaged. Add the driver jar the platform's administrators approve to the module's runtime-libs bundle, rebuild the war and restart, or name a container-managed JNDI DataSource in the property jndi. The user name and the password are the connection's own fields, never part of the URL. The URL must ask for TLS (ssl=true or SSL=1); the certificate is checked against the JVM's trust store, and an option that names a trust store file in the URL is refused.

3. Authentication

A user name and a password: a workload user of Cloudera Data Warehouse, an LDAP account, or the account a Knox gateway accepts. Kerberos is not handled: a URL that carries principal=, AuthMech=1 or a Krb… option is reported when the connection is validated. Two ways round: an endpoint that takes a password (Knox, a virtual warehouse), or a JNDI DataSource whose authentication the container carries (not tried).

4. Boundaries

Only one read-only SELECT and bounded metadata, statistics and sample reads are exposed. Writes, arbitrary statements, stored procedures and job submission are refused. These engines have no read-only connection mode and no transaction, so the promise rests on the statement: a SELECT that runs a script on the cluster (TRANSFORM … USING, MAP … USING, REDUCE … USING) is refused as well.

Impala has no profile operation: the shared profiler asks for several COUNT(DISTINCT …) in one statement, which Impala refuses unless a query option makes them approximate. HiveServer2 names the columns of a SELECT * table.column; the table prefix is dropped from the rows, the preview and the described fields, because a mapping cannot address a dotted name. A join that returns twice the same column name keeps its qualified names: give those columns aliases. When a catalogue scan is asked for row counts, it runs one COUNT(*) per table, which starts one job per table on Hive.

5. What is proven

Against a real server: Apache Hive 4.0.1 (the apache/hive Docker image, embedded metastore, no TLS, no authentication) with the Apache Hive JDBC driver 4.0.1, by tools/live-hive/run.sh. For each of the three profiles (Cloudera Hive, Cloudera Impala over the Hive driver, Apache Spark SQL): connection test, query, named parameters (text with an apostrophe, date, decimal), a quote in a value that changes nothing, truncation, streamed query, preview of a query and of a table, SELECT *, awkward column names, discovery with and without a configured schema, description of a table and of a query, catalogue with comments and row counts, profiling (Hive and Spark SQL profiles) and sampling. The script statement and a write are refused. The generic JDBC engine, played first, fails on that driver for every query, preview, discovery and description, which is why these profiles exist.

Offline, by ClouderaConnectorsTest: the validation rules, the read-only surface, the script refusal, the column renaming, the driver table.

Not proven: Impala itself (only the profile's code path, on Hive), Cloudera's own Hive and Impala drivers (not available), a Knox gateway, a Cloudera Data Warehouse virtual warehouse, the HTTP transport, TLS, a real user name and password, Kerberos, a Spark Thrift Server, large tables, timeouts and cancellation, and the flows of the catalogue and of a mapping inside ON EBX (the operations were called directly).
