ebx-connectors user guide

This guide explains how to configure and operate the module, with the emphasis on mappings. It is written to be read by a person or by an AI agent: every concept is defined once, every mechanism comes with a runnable example, and the last sections give the recipes and the exact calls needed to build a configuration without the user interface. 1. Vocabulary

Term Definition
Connector A configured external application or service: one row of the Connector table (id, type, URL, authentication, properties). Examples: GLEIF, Melissa, Wikidata. The screens call it a connection (menu Connection catalog, Test connection), and keep connector type for the Java code behind it.
Connector type The Java code that knows how to talk to a family of services: gleif, salesforce, jdbc, rest… A type offers operations. Several connectors may share a type (two JDBC databases).
Operation What a connector can do, with its inputs. Three kinds: read (fetch a document for a record, e.g. GLEIF lei), search (fetch a list, e.g. GLEIF searchByName, SAP query), write (send a document, e.g. Salesforce upsert, Kafka publish).
Document The JSON exchanged with the service: what it returns (inbound) or what is sent to it (outbound).
Mapping The translation between a document and an EBX table: a connector, an operation, a direction, a target table, inputs, rules. One row of the Mapping table.
Direction Inbound (INBOUND): the document returned by the operation is written into the EBX record. Outbound (OUTBOUND): a document is built from the record and sent.
Input (MappingInput) A parameter of the operation, computed from the record by an expression: siren = ${./LegalInformation/registrationNumber}.
Rule (MappingRule) A link between a document path and an EBX field, with a transformation pipeline and a write policy.
Transformation A function applied to a value: trim, upper, left(80), map(A=B), fk(/root/T)… Chained with |.
Sub-object A child mapping translating one element of a collection of the document into one row of a child table (addresses, contacts, identifiers).
Import feed An inbound mapping whose operation returns a list (Kafka, SQL query, file, webhook): every item creates or updates a record.
Response mapping The inbound twin of an outbound mapping: it stores in EBX what the service answered to the send (an id, a status).

Language of the screens. The screens are localised in English and French (Messages_en.properties, Messages_fr.properties, in the language of the user's EBX session) and use one vocabulary: connection for the configured object, mapping for its translation between a document and a table, flow (French flux) for a mapping shown on a connection's card, feed for an inbound mapping that returns a list. Localised: labels, tiles and statuses; the cause and next action of the frequent failures (§ 12.1); the common sentences the engine stores in the synchronisation log (created, updated, unchanged, input empty, no data, batch of N, import stopped…, about 25), which a screen writes in the reader's language while the stored text stays English (it is what searches, agents, replay and the REST and MCP answers read; the stored sentence is in the tooltip of the screen's row); the results of the diagnostics (Validate, Test connection, Preview, Connect). Still English: the text stored in SyncLog and returned by REST and MCP, what a connection itself answers (a test message from the remote system, the descriptor validation issues listed by Validate), the technical detail folded under an error, the kernel log, the schema labels of the tables of the Connectors dataset (Connector, Connectors, Connector properties) and the REST and MCP documentation.

2. Where the configuration lives

Everything is EBX data, in the Connectors dataspace, Connectors dataset, created and seeded by the module at startup:

Table Content
ConnectorCategory reference values used to group connectors in the catalog; missing standard categories are added at startup without replacing customer-defined rows
Connector configured connectors (40 seeded, secrets left as TO_BE_SET, to be entered)
ConnectorProperty key = value properties of a connector (options, and the operations of the rest type)
Mapping the mappings, with their inputs, rules and children as associations
MappingInput the inputs of a mapping
MappingRule the rules of a mapping
SyncLog the log: one call = one row (status, message, duration, origin); a feed run in batches writes one row per batch, plus an own row for each failing or conflicting record
Favorite the connectors each user pinned with the star of the connector explorer (own rows only, never edited by hand)

Access: Data > Connectors. On a Mapping row, the dedicated form offers the Design the mapping graphically button. The Synchronise with an external application service is offered on the table view of every table that has at least one mapping. The module's REST API and Data Services read and write the same tables (§ 15).

2.1 Seeding and the customer's model

Connectors are always seeded. The demonstration mappings (on /root/Companies) are seeded only when they make sense in the environment: system property ebx.connectors.seedMappings (-D on the Tomcat JVM):

Value Effect
auto (default) a mapping is created only when its table exists in a dataset of the given name, and only with the rules whose EBX field exists; a mapping whose input references a missing field, a sub-object whose child table, link field or keys are missing, are skipped (one [connectors] seed: line in the log per dropped item)
always everything is seeded as written, as before
never connectors only

Then three validation constraints (warnings, never blocking) watch the configuration permanently, in the validation report of the Connectors dataset and on the forms: Mapping/tablePath (dataset or table not found, link field or keys of a sub-object missing), MappingRule/sourcePath and targetPath (the EBX side of the rule is not a field of the table), MappingInput/expression (a ${./Group/field} does not exist in the table).

A secret left as TO_BE_SET (or empty) is recognised as not set: the connector refuses to call and says why ("set the API key in apiKey"). Secrets are entered in the EBX user interface: the two fields declare EBX's reversible encryption (PasswordTypeEncryption, repository key) and the module decrypts them when it loads a connector. The default osd:password editor would only store a SHA-512 hash, which no connector could use. A value that does not decrypt is used as is, so a key written in clear through Data Services or an import works too, but is then stored in clear. A change of secret, endpoint or property is taken into account at the next call, without restart.

Credential guide. The Connection & configuration tab of a connector shows which credential fields to fill for the selected authentication mode. The modes the connector type offers appear as cards, the others are greyed out. Each credential row carries a state (required, optional, derived, not used) and a contextual label: "API key / token" reads "Client secret" in OAuth 2.0, "Token" in Bearer, "Connection string" for Azure Service Bus. The side panels say what to enter, where to get it at the provider, and what the module actually sends. A length meter warns when a pasted secret exceeds the 255 characters of the field, which is typically a short-lived Entra token pasted in Bearer mode instead of an OAuth 2.0 service principal. The rules live in core/CredentialGuide (type refinements included) and the texts in the credentials.* keys of the Messages bundles. The guide never changes a value: the native EBX widgets keep validation, permissions and encryption.

3.1.1 Secrets, vaults, OAuth 2.0 and mutual TLS

Secret references. Any secret field or property may hold a reference instead of the value, so that the secret lives outside the EBX repository: env:SIRENE_KEY (environment variable), file:/run/secrets/sirene (Docker and Kubernetes secrets), vault:secret/data/ebx/sirene#apiKey (HashiCorp Vault KV v1 or v2; address -Debx.connectors.vault.address or VAULT_ADDR, token -Debx.connectors.vault.token, VAULT_TOKEN or ~/.vault-token, namespace VAULT_NAMESPACE), azurekv:myvault/sirene-key (Azure Key Vault; service principal AZURE_TENANT_ID / AZURE_CLIENT_ID / AZURE_CLIENT_SECRET, or the managed identity of the host), or awssecrets:eu-west-3/ebx/sirene#apiKey (AWS Secrets Manager GetSecretValue; optional versionStage or versionId; static/temporary environment or JVM credentials, a bounded named shared-credentials profile, ECS task credentials, then EC2 IMDSv2—never IMDSv1). ECS and IMDS calls are bounded, refuse redirects, and remain subject to the JVM egress allow-list; or gcpsecret:projects/my-project/secrets/sirene-key (Google Secret Manager; an optional /versions/<version> suffix defaults to latest; explicit GOOGLE_OAUTH_ACCESS_TOKEN, a bounded GOOGLE_APPLICATION_CREDENTIALS service-account document, then Google metadata identity). Google responses are bounded, redirects are refused, and the payload CRC32C is verified when supplied. External-account/workload-identity documents support bounded local-file text or JSON subject tokens, RFC 8693 STS exchange, and optional service-account impersonation. URL, AWS, and executable subject sources are refused. A reference typed in the UI is encrypted like any secret, then resolved when the connector is loaded; resolved values are cached ebx.connectors.secrets.cacheSeconds (300), so a secret rotated in the vault is picked up without restart. A reference that does not resolve makes the connector unusable, with the reason in the error ("Vault address not set", "key 'x' not found in Vault secret..."). Other vaults (CyberArk...) are added with the SecretResolver SPI (§ 3.3): one class, one scheme, declared in META-INF/services/com.on.ebx.connect.spi.SecretResolver. A secret that is neither encrypted by the UI nor a reference is refused unless -Debx.connectors.secrets.allowClear=true (since 2026-10-06).

env: and file: read the machine EBX runs on, on behalf of whoever may edit a connector, and the value then goes to the host that connector names. Their reach is therefore set at JVM level:

Property Effect Default
ebx.connectors.secrets.dir the directory of the secret files (/run/secrets): a file: reference is read only when the file is inside it, .. and symbolic links resolved; a relative reference (file:sirene) names a file of that directory; anything else, an absent file included, answers "no such file in the secrets directory". A directory that does not exist refuses every file: reference. Production setting unset: any file the EBX process can read, ebx.properties included (one warning in the kernel log)
ebx.connectors.secrets.envAllowed what env: may read, as names or prefixes: SIRENE_KEY, EBX_SECRET_* (a lone * matches nothing). A listed name is looked up as a system property (-DSIRENE_KEY=...), then as an environment variable. Production setting unset: any environment variable, and no system property (one warning in the kernel log)

A secret file is 1 MiB at most. System properties are out of reach of env: unless listed because they hold the JVM's own secrets (the Vault token of this module, keystore passwords).

OAuth 2.0 (authType = OAUTH2, for the rest, graphql, soap and any REST-based type): the token endpoint is oauth.tokenUrl, the flow oauth.flow = client_credentials (default), password (username / password of the connector), refresh_token (oauth.refreshToken) or jwt_bearer (oauth.privateKey = PKCS#8 RSA key in PEM, usually a vault: or file: reference; oauth.issuer, oauth.subject, oauth.jwtAudience, oauth.jwtLifetimeSeconds, oauth.claim.<name> extra claims). The client id is oauth.clientId (or clientId), the client secret the API key / token field (or oauth.clientSecret), sent in the form body or, with oauth.clientAuth = basic, as a Basic header; oauth.scope, oauth.audience, oauth.resource and oauth.extra.<name> complete the request. Tokens are cached per connector and renewed a minute before they expire; a 401 drops the token and the call is retried once. Salesforce keeps its own login (client credentials) and accepts oauth.flow = jwt_bearer with a certificate. Its password flow still works but is deprecated: Salesforce retires the OAuth 2.0 username-password flow on 20 February 2027, after which those logins fail. The connector diagnostics and connectors_describe show a warning for such a connection; switch it to client_credentials (or jwt_bearer) before that date.

Mutual TLS and private CAs: tls.keystore (PKCS#12 or JKS with the client certificate), tls.keystorePassword, tls.keyPassword, tls.truststore (a private CA), tls.truststorePassword; passwords may be references. Without them the JVM defaults apply (truststore, proxy settings); there is deliberately no "trust everything" switch. Kafka takes its TLS options through the kafka.ssl.* properties.

SFTP host key: an sftp connector verifies the key of the server against the property knownHosts (path of a known_hosts file on the EBX server) or hostKey (the public key itself, as ssh-keyscan <host> prints it; several keys may be given). With neither, it refuses to connect and says which property to set: an unverified server can be anyone on the path, and it receives the password. strictHostKey = false connects without verification, with a warning in the kernel log; it is meant for a test server.

Webhooks: the sender authenticates as an EBX user (Basic or token) holding the RUN right, and the import runs under that technical account. The shared-secret (X-Webhook-Secret) and signature (X-Webhook-Signature) modes no longer exist, and a connection of type webhook stores no secret and no account.

JDBC connections: a connector row is data, but a JDBC URL, a driver class, a JNDI name and the jdbc.* properties are what the server loads or runs. By default a JNDI name must start with java:comp/env/, the driver class must be the one of the URL's sub-protocol, the options that load a class, run SQL or read or write a file are refused (H2 INIT, socketFactory, sslfactory, loggerFile, MySQL allowLoadLocalInfile, autoDeserialize...), an H2 URL must be tcp:, ssl: or mem:, and an in-memory H2 refuses CREATE ALIAS and file functions. Each refusal names the ebx.connectors.jdbc.* property of the table above that allows it.

Who may edit connectors: a baseUrl sends EBX data wherever it points. Reserve the Connectors dataset to an administration role, and keep the history of the Connector table on.

A run whose rows are purged can no longer be replayed or resumed. Two outbound rules apply whatever the settings. Link-local and cloud metadata addresses (169.254.0.0/16, fe80::/10, fd00:ec2::254, metadata.google.internal, the Alibaba and Oracle metadata addresses) are refused, by literal address and by the addresses a name resolves to, unless an exact entry of the allow-list names the host: they hand out the credentials of the machine. (A call that leaves through the JVM's HTTP proxy is judged on the host written in its URL: the proxy resolves the name.) The module's own workload-identity lookups (awssecrets:, gcpsecret:, azurekv: with the identity of the host) are not concerned, but stay subject to the allow-list when there is one. Redirects are never followed blindly: at most 5 hops, each one checked like a first call (allow-list and address rules); when a hop leaves the host or port that was called, only Accept, Accept-Language and the Content-* headers travel on, so Authorization, API-key headers, cookies and signatures stay with the server they were meant for; a redirect to another scheme (https to http or the reverse) is returned as it is. The same rules cover the download of an OpenAPI specification by URL (http or https only, 16 MiB at most). For production: set ebx.connectors.allowedHosts, ebx.connectors.egress.requireAllowList=true and, where it fits, ebx.connectors.egress.privateExceptions for the private hosts the connectors really call (the private-host block itself is on by default).

Whatever the settings, the texts the module keeps or returns (sync log, REST answers, workflow outputs, kernel log) are redacted: the secret values of the loaded connectors, the secret query parameters of URLs (key, api_key, token, signature...) and echoed Authorization headers are replaced by ***. Since ebx.connectors.secrets.allowClear is not true by default (§ 3.1.1) the repository does not serve a secret in clear. Together with the vault references, OAuth 2.0 and mutual TLS of § 3.1.1, this is the set an architect expects before a production deployment; what remains is the customer's: the history of the Connector table, the retention of EBX's own audit, and the governance of what the LLM connectors are allowed to receive. That includes images and scans when a documents connector has vision = true (§ 14.8): photos, signatures and identity documents then reach the model provider.

3.1.3 Who may do what: the three Connectors rights

Nothing is open by default. A caller who is neither an EBX administrator nor a member of a role that holds one of the three rights below is refused every MCP tool (on /ebx-connectors/rest/mcp, on the native MCP server and on the in-JVM bridge alike), every REST route of /ebx-connectors/rest/v1 (answer 403) and every user service of the module (the action is neither shown nor executable). tools/list only lists the tools the caller may call.

Right Default role What it opens
READ (viewer) ConnectorsViewer list and describe the connections (secrets masked), list and read the mappings, read a run and the sync log, plan a catalog source; the Connection catalog and Connector operations screens
RUN (operator) ConnectorsOperator READ, plus: connectors_sync, connectors_enrich, connectors_replay, connectors_run_stop, connectors_publish, connectors_lineage_declare; the outbound documents and the conflicts (they carry record values) and the decision on a conflict; the "Synchronise with an external application" action and the conflict manager
MANAGE (designer) ConnectorsDesigner RUN, plus: every change of configuration (connectors_mapping_upsert, connectors_mapping_delete, connectors_config_import, connectors_openapi_import, templates, applying a catalog source), connectors_config_export, connectors_call (any operation of a connection, with its stored credentials), describing the fields of an operation (it samples the remote system); the mapping designer, the diagnostics, the OpenAPI import and the deletion of a mapping

Giving the rights: the "Access rights" table. An administrator maps the rights onto roles that already exist in the directory, in the user interface: perspective Data connector → Administration → Access rights (table AccessRight of the Connectors dataset). One row = one role of the directory (picked from the list of existing roles, or "Everyone") and its right; a comment says why. A person receives the widest right any of their roles brings. A change applies within a few seconds, without a restart. Only an EBX administrator can edit this table: a designer cannot give rights.

The default language-model connection: the "Settings" group. The other ON EBX modules (MDM Factory, data catalog) ask a language model through Connectors; when they do not name a connection, they get the one an administrator chose in Default language-model connector, in the group Settings of the Connectors dataset (dataspace and dataset Connectors, navigation pane). Only a connection of type llm is accepted. Empty: the JVM property -Debx.connectors.llm.default, else the only usable llm connection when there is exactly one. Read at each call, no restart. Only an EBX administrator changes it. Whatever a module asks, an answer is never longer than the maxTokens property of the connection (1024 unless set): raise it on the connection when a module needs longer answers.

Without any row, three role names work out of the box (ConnectorsViewer, ConnectorsOperator, ConnectorsDesigner): create them in the directory if you prefer dedicated roles. They can be renamed with -Debx.connectors.role.viewer, -Debx.connectors.role.operator and -Debx.connectors.role.designer (-Debx.connectors.adminRole is still read as the designer role). The table and these roles add up. A refusal is written to the kernel log ([connectors] access denied: user ..., tool ...).

Three things to know:

  • Workflows and scheduled tasks are not concerned. A workflow script task, a scheduled task and the table trigger run what a designer configured, under the session EBX gives them; the control point is who may configure the mapping and publish the workflow.
  • A webhook needs an EBX user with the RUN right; the shared secret and the signature were removed.
  • The rights open the module's entry points, not the tables. Reading or editing the rows of the Connectors dataset through EBX itself (user interface, data services) stays governed by the EBX permissions of that dataset, plus the access rule of § 3.1.2 when the designer role is set by property.

Calls that change something must not come from another site. A POST, PUT, PATCH or DELETE on /ebx-connectors/rest/... (the MCP endpoint included) is accepted only with an Authorization header (what curl -u, a script or an MCP client sends), or an X-Requested-With header, or from a page of this EBX (the browser's Origin names the same host and port). Anything else is answered 403 and written to the kernel log ([connectors] cross-site request refused: ...): a page of another site cannot ride the session of a signed-in user. Send the credentials with the request itself: a client that waits for a 401 before authenticating may get this 403 instead.

Who ran or changed what. Every MCP tool call and every REST route that asks RUN or MANAGE leaves one line in the kernel log, whether it succeeded, failed or was refused: [connectors] audit: user=alice tool=connectors_sync mapping=12 dryRun=true outcome=ok ms=532 (a REST route reads rest=sync ... status=200). The line names the user, the tool or route, the connection, mapping, run or conflict concerned, the outcome and the duration; it never carries a document, an input, a record key or a secret. Reads are not traced. Actions started from the screens, workflows and scheduled tasks are found in the sync log and the runs, not in this line.

3.2 A REST connector without Java: the rest type

The rest type is declared entirely through properties, one operation = three properties:

op.<name>.method = GET | POST | PUT | DELETE     (GET/DELETE = read, POST/PUT = write)
op.<name>.path   = /w/api.php                    ({placeholders} = mapping inputs, URL-encoded)
op.<name>.query  = action=wbsearchentities&search={name}&language=en&format=json&limit=1

A real example, the Wikidata connector (baseUrl = https://www.wikidata.org, auth NONE):

op.search.method = GET
op.search.path   = /w/api.php
op.search.query  = action=wbsearchentities&search={name}&language=fr&format=json&limit=1&type=item
op.claims.method = GET
op.claims.path   = /w/api.php
op.claims.query  = action=wbgetclaims&entity={id}&format=json

The mapping provides name (or id) as an input; the returned document is the raw JSON of the API.

3.3 A connector in Java

A class implementing com.on.ebx.connect.spi.Connector (or extending AbstractRestConnector): getType(), getLabel(), getOperations(), configure(ConnectorConfig), execute(context, operation, inputs, outboundDocument) returning a JsonNode (or null = no data), and optionally describeFields(...) to feed the designer. Built-in types are registered in ConnectorRegistry.

Without the module sources: an extension jar. The module also loads every implementation declared through the standard java.util.ServiceLoader mechanism, so a third party adds a type by shipping a jar:

  1. compile against dist/ebx-connectors-spi.jar (built by build-spi.sh: the spi package plus the AbstractRestConnector, HttpJsonClient and Json helpers; a sources jar sits next to it), with ebx.jar (or ebx-lib.jar on FastTrack) and Jackson on the classpath, Java 8 syntax (--release 8);
  2. add the file META-INF/services/com.on.ebx.connect.spi.Connector containing the class name (one per line); the class needs a public no-arg constructor;
  3. drop the jar into ebx-connectors/WEB-INF/lib/ (third-party libraries the connector needs go there too, or to Tomcat's shared lib), restart: the type is in the Connector/type list, its operations and fields in the designer.

The project ebx-connectors-extension-sample (next to the module) is a complete, buildable example: an OpenStreetMap Nominatim geocoder (nominatim type, operations geocode and reverse, a user.agent property turned into a request header by overriding headers()), its build.sh, its services file and Eclipse files. Copy it to start your own connector.

The same jar may declare a secret resolver (com.on.ebx.connect.spi.SecretResolver: one scheme, one resolve(reference) method, listed in META-INF/services/com.on.ebx.connect.spi.SecretResolver) to read secrets from another vault (§ 3.1.1).

3.3.1 Publishing a whole product: the TablePublisher SPI

A connector able to receive a whole data product (§ 10.2) additionally implements com.on.ebx.connect.spi.TablePublisher, EBX-free like the rest of the SPI: nativeType(column) (the native type used for a column, for reports and DDL), plan(spec, recreate) (the statements a real run would execute, nothing run — the dry-run path), prepare(ctx, spec, recreate) (schema, control table, target and staging tables; returns CREATED/EXISTS/RECREATED per table), load(ctx, spec, table, documents) (loads one batch into a table's staging area), commit(ctx, spec, rowsPerTable) (the single atomic step: every target table replaced by its staging content, in one request), and cleanup(ctx, spec) (drops the staging tables, best effort, called after commit and after any failure). Identifiers (schema parts, table and column names) are validated and upper-cased by the caller ([A-Z_][A-Z0-9_]*) before the SPI ever sees them; the implementation only needs to double-quote them. connectors/SnowflakePublicationSql (package-private, dependency-free, unit-tested directly) is the reference implementation, consumed by SnowflakeConnector implements TablePublisher: type mapping, DESCRIBE TABLE/CREATE TABLE/CREATE OR REPLACE TABLE, a FLATTEN-based batch insert into a __STG staging table, and a single multi-statement BEGIN … COMMIT request (Snowflake SQL API parameter MULTI_STATEMENT_COUNT) for the atomic commit. core.ProductPublisher (§ 10.2) is the only caller of this SPI; a connector that does not implement it simply cannot receive a publication (connectors_publish answers a clear ERROR naming the connector and its type).

3.4 Creating a connector from an OpenAPI specification

The module reads an OpenAPI 3 specification (JSON, or YAML thanks to jackson-dataformat-yaml and snakeyaml, which the war carries since 1.4.1; a YAML specification over 3 MiB is refused) and turns it into a connector of type rest:

In the specification In the connector
servers[0].url (variables replaced by their default) baseUrl; relative → to complete by hand, reported
securitySchemes: apiKey in header / in query, http basic, http bearer, oauth2 authType + apiKeyHeader (or property auth.apiKeyQuery); the secret stays to be entered
each paths.{path}.{get\|post\|put\|delete} op.<operationId>.method / .path / .query (query parameters as name={name}); without operationId, the name comes from the path
path parameters and required parameters op.x.required (list; - = none mandatory); the others are optional and not sent when empty

3.5 Power BI for the data catalog: the powerbi type

PowerBiConnector reads a Power BI tenant for the data catalog (ebx-data-catalog): reports, dashboards, semantic models with their tables, columns, calculated columns and measures (DAX kept as the column's expression), dataflows and their entities, and the lineage between all of them and their data sources. It needs no library: Power BI REST API v1.0 over HttpJsonClient.

Connector row: baseUrl = https://api.powerbi.com/v1.0/myorg, authType = OAUTH2, properties tenantId and clientId (a Microsoft Entra service principal), the client secret in apiKey; the token endpoint and the scope https://analysis.windows.net/powerbi/api/.default are derived. A user token in apiKey with authType = BEARER also works for a quick try. If the outbound allow-list is enforced (§3.1.2), allow api.powerbi.com and login.microsoftonline.com.

Two scan modes (property scanner, default auto):

  • admin — the Scanner API (admin/workspaces/getInfo with lineage, datasourceDetails, datasetSchema, datasetExpressions, then scanStatus polling and scanResult; dataflow definitions through admin/dataflows/{id}/export). Tenant-wide, with table schemas, Power Query M and DAX. The service principal must be allowed by three tenant settings: Allow service principals to use read-only admin APIs, Enhance admin APIs responses with detailed metadata and Enhance admin APIs responses with DAX and mashup expressions.
  • standard — groups, reports, datasets, dashboards (+ tiles), dataflows of the workspaces the principal is a member of: objects and links only, no schema, no expression.
  • auto tries admin and falls back on standard on a 401/403. testConnection says which mode is available.

Operations (all inbound; source = the catalog source id, prefix of every asset key; schemas = comma-separated workspace names or ids, empty = every non-personal workspace):

Other properties: include.personal, include.hidden, dataflow.definitions, scan.timeout (seconds), max.workspaces, portal.url (asset URLs), max.rows (DAX query). Verified offline only: PowerBiScanTest (a recorded scan result → exact catalog and lineage documents) and PowerBiConnectorTest (a fake tenant: token, Scanner API polling, activity log, refresh history, DAX query, standard fallback), both in build-test.sh. Nothing has been run against a real tenant.

3.6 Collibra, both directions: the collibra type

CollibraConnector talks to a Collibra Data Intelligence Platform through its REST API 2.0 (https://<instance>.collibra.com/rest/2.0, the suffix is added to baseUrl). authType = BASIC (a Collibra user with API access) or BEARER / OAUTH2 (a JWT from the identity provider of the instance). 3.7 Lineage of every data flow: the openlineage type

Declare one connector of type openlineage — base URL = the endpoint that accepts OpenLineage RunEvents, with its authentication — and every outbound run of the module describes itself there, nothing else to configure:

Endpoint Base URL Authentication
ON EBX data catalog (ebx-data-catalog) http://host/ebx-data-catalog/rest/v1/openlineage EBX Basic
Marquez http://marquez:5000/api/v1/lineage none / API key
DataHub, Atlan, OpenMetadata... their OpenLineage ingest endpoint as documented there

One event per mapping and per run (ConnectorService.beginRun() / endRun(): a REST call, a workflow step, a scheduled run, a user-service run; a table trigger or a single call sends its own):

  • job = the mapping (namespace job.namespace, default ebx-connectors; name = the mapping's label);
  • inputs = the EBX table, named as the data catalog names it — namespace ebx.namespace (the lineageNamespace of the EBX source in the catalog, default ebx://localhost:8080), name <dataspace>/<dataset><tablePath> (Companies/Companies/root/Companies);
  • outputs = the connector's object: namespace from the connector's base URL (h2://localhost:9092/catalogdemo, postgresql://db:5432/mdm, snowflake://acme.snowflakecomputing.com, salesforce://acme.my.salesforce.com...), name from the mapping's object input (table, prefixed with the connector's schema property when it has no dot; object, sobject, topic, path...), else the operation name — so that it matches what a scan of the same platform creates. On a broker (kafka, rabbitmq, jms, activemq, azure-service-bus) the object is the topic / queue input, else the connector's topic property — never the table input, which only labels the document there; a base URL without a scheme (localhost:9082, broker1:9092,broker2:9092) gives kafka://localhost:9082, the first bootstrap server;
  • columnLineage on the output: one entry per rule with a source (Identification/Name → NAME, subtype IDENTITY, or TRANSFORMATION with the pipeline as description; constants left out);
  • sub-object mappings, at any depth, bring their own EBX table (dataset and dataspace of the root when they have none): outbound, the child table is an extra input and the document fields collection[].field point at it, not at the root table; inbound, the child table is an extra output whose fields point at collection[].field of the connector's object;
  • run facets: outputStatistics.rowCount = records sent, errorMessage when nothing went through (eventType FAIL), and ebx_connectors (run id, mapping, connector, operation, sent / deleted / failed / skipped). The OpenLineage runId is derived from the Connectors run id and the mapping, so a replay updates the same run.

Properties of the sink: emit.outbound (default true), emit.inbound (default false: imports and enrichments described too, EBX becoming the output and the rules read the other way), exclude.types (default chat-webhook,slack,openlineage,llm), exclude.connectors (ids), producer. Nothing is sent for a simulation or for a run where no record went through; a sink that refuses an event is logged (WARN, kernel log) and never fails the synchronisation. The list of sinks is re-read every thirty seconds (at once when a sink is edited). Operation emit posts a hand-built event (or an array) as is, for an outbound mapping that builds its own events.

Declared lineage: before the first run

A flow shows in the catalog as soon as it is declared, not only after it has run. The triggers of Mapping, MappingInput and MappingRule (MappingCascadeTrigger, MappingPartLineageTrigger) hand the mapping to core/DeclaredLineage, which describes it two seconds after the last change — outside the transaction, so that a designer save or a configuration import gives one event per mapping and reads the committed definition:

  • an active root mapping is sent as an OpenLineage JobEvent (no run, no eventType): the same job name, datasets and column lineage as a run event, plus the job facet ebx_connectors_declaration (state DECLARED, mapping, connector, operation, direction). A sub-object mapping is described with its root, its table included, inbound as well as outbound;
  • writes that run without triggers schedule the same declaration themselves: the MCP tools connectors_mapping_upsert and connectors_mapping_delete (and the REST DELETE /mappings/{id}), the deletion also describing again the root the sub-object mapping belonged to;
  • a deactivated or deleted mapping, and the old name of a renamed one, is sent as a retirement: a JobEvent without datasets (state RETIRED);
  • at repository startup every mapping is swept once (after 90 s, retried twice two minutes apart when a sink was not reachable yet), which also catches up the mappings declared before this existed;
  • on request: POST /ebx-connectors/rest/v1/lineage/declare[?mapping=<id or label>] or the MCP tool connectors_lineage_declare — after adding a sink or changing a connector's base URL (changes to a connector are not watched).

The data catalog takes a job event as the job's whole current lineage: edges written with origin DECLARED (confidence 90) unless already observed, the job's edges it no longer lists deactivated, the job's last run left untouched; the first run then turns the edges into OPENLINEAGE. The sink property emit.declared (default true) turns declarations off for one sink; the direction and exclusion properties apply as for runs (an inbound mapping is declared only with emit.inbound=true). System properties: ebx.connectors.lineage.declared (default true, the whole mechanism), ebx.connectors.lineage.declareOnStartup (true), ebx.connectors.lineage.startupDelaySeconds (90), ebx.connectors.lineage.debounceMs (2000). The triggers are declared in the model: they take effect after the Connectors model is reloaded and Tomcat restarted.

Recognising the ON EBX data catalog (core/CatalogDetection)

The module never takes a dataset for the data catalog because of its name: a customer may have a DataCatalog dataset of its own, with nothing in common. Two independent checks, and on doubt nothing is proposed or written:

  • local — the dataset -Debx.catalog.dataspace / -Debx.catalog.dataset (default DataCatalog / DataCatalog, the JVM properties the catalog reads too) is the catalog only when its data model is /WEB-INF/ebx/schemas/DataCatalog.xsd packaged by module ebx-data-catalog (Adaptation.getSchemaLocation()). A DMA publication, another module's model or an unreadable one is FOREIGN: its Sources are never read, and the advice says why;
  • remote — an openlineage connector's endpoint is the catalog only when its new read operation contract (GET on the base URL) answers module = ebx-data-catalog, with contractVersion, features (runEvents, jobEvents, sources) and datasetState (VERIFIED, ABSENT, FOREIGN). Read at most every five minutes per sink and base URL. A catalog that announces no jobEvents, or whose dataset is FOREIGN, receives no declaration; any other answer, or none (Marquez, DataHub, a catalog older than the contract), leaves the sink exactly as before.

connectors_mapping_upsert and connectors_mapping_delete answer a lineage block, and connectors_lineage_declare (REST POST /lineage/declare) the same without the mapping part: declaration (scheduled, retirement scheduled, not scheduled for a dry run, or disabled), the connector's OpenLineage namespace, catalog (state, dataspace, dataset, reason, and source = the catalog Source whose lineageNamespace is that namespace), sinks (id, what the endpoint is, contract version and features, takesThisMapping) and advice: create an openlineage sink when the catalog is deployed and nothing feeds it; point one at the catalog when none answers as such; create the Source of the system, or set lineageNamespace on the Source that already names this connector, when no Source has the namespace (otherwise the catalog files the lineage under a separate source created for that namespace); and when the namespace is held, but by a Source without connector — one the catalog created from lineage events — while another Source names this connector, say that the system is listed twice and which Source to fix (catalog.sourceConnector is then empty). Seen on 2026-09-15 with the Snowflake demo: OL_SNOWFLAKE_ACCOUNT_… held snowflake://ACCOUNT.snowflakecomputing.com, SNOW_DEMO another namespace. Offline contract: src/test/.../core/CatalogDetectionTest.

The catalog's own flows are not lineage. The mappings the catalog writes for itself — Catalog scan, profile, sample, usage, lineage, jobs, access grant / revoke, alert, the Collibra publication — have the catalog dataset as their EBX side. Described as lineage (as they were until 2026-09-15 with emit.inbound=true), they showed up in the catalog as "tables" named after their operation (catalog, profile, execute…) under the platform's source. exclude.catalogFlows (sink property, default true) leaves them out: no run event, and at each declaration (startup sweep, change) a retirement instead, which deactivates the edges an earlier version declared. Only a verified catalog dataset counts (CatalogDetection.isCatalogFlow); the flows of a customer's same-named dataset are described as any other. The assets and columns those declarations created stay: delete them once. connectors_lineage_declare reports such a mapping as RETIRED_CATALOG_FLOW (counted in retired), not DECLARED.

Naming the connector's side. The object an input names (table, topic, entitySet…, with the connector's schema in front of a bare table) — else, for a feed that only carries a query (sql, query, statement), the first table of its FROM (quotes, backticks and brackets removed; a templated table is not guessed) — else the operation name, which then stands for an API endpoint (search for Wikidata). Until 2026-09-15 the Snowflake and Databricks query feeds appeared as a table named query.

The catalog Source of a connector (connectors_catalog_source, REST POST /lineage/catalog-source). Parameters connector, optional source (id of a Source to create, default from the connector id) and apply (default false: the plan only). Only a verified catalog is read or written, with the caller's permissions, and nothing is ever deleted. From the Source holding the connector's namespace and the Sources naming the connector: LINKED (nothing to do), CREATE (no Source: id, label, platform guessed from the namespace, connector, lineageNamespace), SET_CONNECTOR (the Source the catalog created from lineage events for that namespace gets the connector), SET_NAMESPACE (the Source naming the connector gets the namespace), MANUAL (the system listed twice, a namespace held by another connector, several Sources for one connector, an id already taken: explained, nothing written). The catalog's source trigger then creates or realigns the flows of the Source; run connectors_lineage_declare so that the lineage lands on it. The lineage advice of the mapping tools names the tool.

Connector changes. ConnectorLineageTrigger (Connector table) sends the declared lineage of a connector's mappings again when its type, base URL or activity changes — the namespace comes from those fields — and the configuration import, which writes without triggers, does the same for the connectors whose fields changed and for those whose mappings it brought. Before 2026-09-15 a base URL change needed a manual connectors_lineage_declare. The trigger is declared in the model: model reload and restart.

3.11 Slack with a bot token: the slack type

The chat-webhook type posts to one channel through an incoming-webhook URL, and that URL is the secret: it sits in the base URL, in clear. 4.2 Life cycle of an inbound mapping on a record

  1. The inputs are computed from the record (§ 5). If a required input of the operation is empty, the call is SKIPPED ("Input 'lei' is empty on this record").
  2. The connector executes the operation; null = NO_DATA.
  3. responseRoot is applied to the document.
  4. Each rule reads its source in the document, applies its pipeline, and writes its target according to its policy: IF_EMPTY writes only when the EBX field is empty, ALWAYS overwrites, TRUSTED arbitrates by trust (see 4.4).
  5. The sub-objects are processed (§ 8), everything is saved in one transaction, and a SyncLog row is written: OK (at least one change), NO_CHANGE, or ERROR.

The same mapping runs in simulation (dryRun): changes are computed and shown, nothing is written.

4.4 Trust, provenance and conflicts

When two sources disagree, the module decides by trust:

  • every connector carries a trust level from 0 to 100 (Connector/trust). Seeded values: GLEIF, Sirene, Companies House 90; D&B, Orbis, Handelsregister 85; VIES, Creditsafe, OpenSanctions 80; Melissa, Loqate 75; BAN, OpenCorporates, SAP, JDE 70; Google, CRM and ERP 60; Wikidata 40; default 50. A manual entry, or a value loaded outside the connectors, counts as 100;
  • every write by a connector is remembered in the FieldProvenance table (record, field, connector, trust, value, date), whatever the rule policy: this is the audit trail;
  • the TRUSTED rule policy writes when the field is empty, or when the source is at least as trusted as the one that wrote the current value (so a source refreshes itself, and a better one corrects a worse one). Otherwise the proposal is logged in the Conflict table (current value, who wrote it and with which trust, proposed value, by whom, when), status OPEN, for a steward to decide: apply the value by hand and set the conflict to ACCEPTED, or set it to REJECTED. The same conflict is logged once while it stays open.

IF_EMPTY and ALWAYS remain available and unchanged. The report of a call (log, REST API, workflow bean) counts the conflicts, and the API details them (results[].conflicts).

Example: the legal name of Microsoft France was written by VIES (trust 80). The Recherche d'entreprises API (85) proposes "MICROSOFT FRANCE": with TRUSTED it wins and overwrites. Wikidata (40) proposing something else would be logged as a conflict without any change. A name corrected by hand (100) is never overwritten by a connector again.

4.5 Managing conflicts

A conflict is a steward decision. Three ways to know there are some:

  • REST API: every answer of /enrich, /sync/{mapping} and /webhook/{feed} carries conflicts (count) and hasConflicts (boolean), and each result details its own in results[].conflicts. GET /ebx-connectors/rest/v1/conflicts?dataset=Companies&table=/root/Companies&key=513 lists the open conflicts (status=ACCEPTED|REJECTED for the history);
  • workflow script task: the bean returns conflictCount and hasConflicts (true/false), to test in a condition (ConditionIsValueEqualsTo, value1=${hasConflicts}, value2=true) that routes to the user task below;
  • log: the message of every call counts the conflicts.

The "Manage connector conflicts" screen (a user service of the module) lists the open conflicts with, for each field, the current value (who wrote it, its trust) and the proposed value (by whom, its trust). For each row: Take the proposed value (the value is written into the record, the proposing source becomes the provenance of the field, the conflict becomes ACCEPTED), Keep the current value (REJECTED) or Decide later. A common comment is stored on the decided conflicts, with the user and the date. It is available:

  • on a dataspace (Actions menu, or perspective action): every conflict of the dataspace;
  • on a table (Actions menu of the view): those of the table;
  • on a record: those of the record;
  • on the Conflict table of the Connectors dataset itself: the whole open backlog, or only the conflicts selected in the view (the service on a conflict record opens that single conflict);
  • as a workflow user task (service ebx-connectors@ConflictManager): input parameters branch (required), dataset, table, recordKey (optional, they narrow the list); outputs resolvedCount and remainingCount. The Complete the task button closes the work item.

Through REST, a decision is POST /conflicts/{id}/accept?comment=... or .../reject.

The ConnectorEnrichment workflow chains: enrichment script task, condition on hasConflicts, user task "Resolve the conflicts" offered to the administrators.

4.6 Deleting a mapping

A mapping has attachments: rules, inputs, sub-object mappings, outbound states, and provenance and conflict rows that reference it. Deleting the Mapping row alone would leave them orphaned, so the Mapping table carries a cascade trigger (MappingCascadeTrigger): whatever the way a mapping is deleted (user interface, Data Services, import, service), its rules, inputs, sub-object mappings and outbound states go with it, and the provenance and conflict rows keep their history but lose the reference. The synchronisation log is kept as is.

The user service Delete this mapping and everything attached (on a Mapping record, or on the rows selected in the Mapping table) shows what will be deleted and what will only be unlinked, then asks for confirmation. The same deletion is available as DELETE /ebx-connectors/rest/v1/mappings/{id} and as the MCP tool connectors_mapping_delete. Export the configuration first (GET /rest/v1/config) if the mapping may be needed again.

5. Inputs and expressions

An input = name (the one the operation expects) and expression. Expression syntax:

Form Result
${./Address/City} the value of the record field, in XML Schema format (ISO dates, FK = key)
${./A} ${./B} juxtaposition: concatenation with the surrounding text
${param.max} a parameter passed at run time (workflow, API)

${./Address/City\|capitalize\|left(40)} a pipeline on one placeholder

The available transformations are those of the rules (§ 7), map, fk and lookup included. An unknown transformation fails the call with an explicit message. Examples:

vat      = ${./LegalInformation/registrationNumber|vatfr}                 (SIREN -> FR + key + SIREN for VIES)

In the designer, the Service call panel lists the inputs of the operation (required ones starred), with an EBX field picker and transformation chips.

Placeholders can be nested: ${./LegalInformation/registrationNumber|default(${./Identification/Name|upper})} sends the SIREN when present, else the upper-cased name. The inner placeholder is resolved first, then serves as an argument of the outer transformation.

Run-time inputs of a feed. A feed starts from no record, so its inputs are constants — unless an expression reads a run-time parameter. With tables = ${param.tables|default(*)} a run given nothing reads every table, and a run given tables=SALES.ORDERS reads that one only. Run-time inputs are text, name=value pairs separated by ; (tables=SALES.ORDERS,SALES.CUSTOMER;limit=50), and every way of running a feed accepts them: inputs= on POST /sync/{mapping}, the inputs parameter of the workflow bean and of the scheduled task, and the inputs URL parameter of the user service (§ 12). Only the names an input expression of the mapping reads as ${param.name} are used; the others are not used, and every run says so: ignoredInputs (and inputsIgnored, kept for the first REST callers), warning: true and a sentence in message in the MCP and REST answers, whose plain OK then reads WARNING (PARTIAL, ERROR, NO_DATA and RUNNING are left as they are); a message in the user service, next to any other message of the run; the warnings output of the workflow bean and the first line of its report; an execution line starting with WARNING: in the task scheduler. A run on one record, on the records of a table or on an outbound scope reads no run-time input: every one it is given is reported the same way. A run-time input narrows what the mapping already allows; it never adds an input the mapping does not use, so a link or a script cannot slip a sql or a where into a feed that has none.

How much one run takes (max). max bounds what ONE run takes: the records of a table or of an outbound scope, or the items a feed imports. Its default depends on how the run is started, and is defined in one place (com.on.ebx.connect.core.RunLimits):

Started from Parameter Default

MCP connectors_sync (and the in-JVM bean), REST POST /sync/{mapping}, workflow bean ConnectorScriptTaskBean max / maxRecords 200
User service, on records or a scope Maximum number of records 100
User service, on a feed Maximum number of records 499 (4,999 at most for a simulation)
REST POST /webhook/{feed} max 10,000 (also the ceiling)
Publication of a data product (connectors_publish, POST /publish, ProductPublishTaskBean) max / maxRecords 0 = every row

A run cut at max always says so, whatever started it: a "Limit reached" result closes its results (with the number of items the source returned when the connector knows it), its answer carries truncated: true and the sentence in message, its status is PARTIAL, never OK, the user service shows the notice under its counters, the workflow bean sets truncated, and the scheduled task fails on it, unless it is draining a backlog (an outbound scope, a table filtered by a predicate), where it says it. The count of an answer counts the records processed, not that notice. A connector's own max.rows property (1,000 for a JDBC source) is something else: what the connector returns when it is called without max (connectors_call, a preview); the engine always hands its max to the connector when it runs a feed.

6.3 Policy and order

IF_EMPTY (default) respects existing data; ALWAYS overwrites; TRUSTED overwrites only when the source is at least as trusted as the one that wrote the value (4.4). Rules apply in position order.

IF_EMPTY writes a field once: when a feed runs again after its source changed, a field already filled keeps its value, and the run reports NO_CHANGE. A feed that must follow its source needs ALWAYS on the rules of the fields that change, its key fields (what its key predicate reads, the child key fields and the parent link field of a sub-object mapping) staying IF_EMPTY. The policy is therefore a choice on a feed: the mapping designer asks for the policy of the rules added to a feed or a sub-object mapping (with this explanation), gives it to every new rule except the key fields, and can apply it to the rules already there. connectors_mapping_upsert and the configuration import keep IF_EMPTY for a rule sent without a policy, and their answer says what was applied: rulePolicies (rules per policy), policyDefaulted (rules written IF_EMPTY because they had none) and, on an inbound mapping, a note in notes saying what that means. Outbound, source and target swap: source = EBX field, target = JSON path of the document being built (primaryAddress.addressLocality.name).

10. Outbound direction and response mapping

An outbound mapping builds a document from the record (rules source = EBX field, target = JSON path, sub-objects = collections) and sends it through a write operation (upsert, publish, merge, create). What the service answers (a created id, a status) is stored by the response mapping: an inbound mapping, same connector, same operation, same table, which the framework applies automatically to the answer. The designer shows it and the Create the response mapping button creates it. For a read operation (Melissa address, VIES, GLEIF), one inbound mapping is enough: its inputs are the send, its rules the answer.

10.1 Deltas, deletions and replay

An outbound run takes a scope (scope= in the API, the Records list of the user service, the scope parameter of the workflow bean and of the scheduled task):

Scope Records sent
all (default) every record of the request, as before
unsent records never sent successfully by this mapping
changed records whose outbound document differs from the last one sent (fingerprint), failures allowed by the retry policy, and the deletions
failed records whose last send failed and that the retry policy allows again
dataspaceDelta records created, modified or deleted in the dataspace since its initial snapshot (EBX comparison API); the dataspace must be a child dataspace

The table OutboundState (one row per mapping and record) remembers each delivery: status SENT (with the fingerprint and the last document), FAILED (with the error, the number of attempts and the last attempt time) or DELETED. Only successful sends update the fingerprint, so a failed record is naturally resent by changed, and a modification made by an inbound enrichment is resent too.

Deletions are propagated when the mapping declares a deleteOperation: the connector operation called for a record that disappeared (changed: present in OutboundState, absent from the table; dataspaceDelta: present in the snapshot only). The call receives the inputs of the mapping resolved on the snapshot record when there is one, plus key (the primary key) and the scalar fields of the last document sent. Without deleteOperation, deletions are ignored.

Retry policy, per mapping: maxAttempts (5) and retryDelayMinutes (30). A record in FAILED is retried by changed and failed until the attempts are exhausted or while the delay has not elapsed it is counted as "waiting"; after that it stays FAILED until a manual replay.

Simulation. With dryRun=true an outbound run builds every document and shows it (changes) without calling the service; the outbound state is not touched.

Runs and replay. Every execution (a REST call, a workflow step, a scheduled run, a user service run) gets a runId, written on each SyncLog row and returned by the API and the workflow bean. POST /ebx-connectors/rest/v1/replay/{runId} re-runs the calls of that run that ended in ERROR, inbound or outbound, on the current version of the records (a record that disappeared is skipped, or deleted remotely when the mapping has a deleteOperation). GET /runs/{runId} gives the state of a run and a page of its calls (50 newest first; callsMax up to 500, callsFrom for the next page) and says whether it is replayable; GET /outbound?mapping=&status=FAILED lists the records to replay of a mapping (status=SENT|DELETED|ALL for the rest).

# the delta of a child dataspace, in simulation
curl -u admin:admin -X POST "http://localhost:8080/ebx-connectors/rest/v1/sync/7?scope=dataspaceDelta&dryRun=true"

10.2 Publishing a data product as a whole

A consumer of a data product must never rebuild it from the member tables one delta at a time. Where § 10.1 sends one mapping's records over time, publishing a product (core.ProductPublisher, MCP connectors_publish, POST /publish, workflow bean ProductPublishTaskBean) sends one or more root outbound mappings, all on the same connector, as a single unit against a contract (the exposed columns), with one cut-off and one atomic commit for every table. v1 scope: Snowflake only, full reload only (every target table is entirely replaced at each publication, there is no incremental/delta mode here — that is what § 10.1 is for), a product = one Snowflake table per root mapping. A root mapping's active children (sub-object mappings) are not published as separate tables: each becomes a VARIANT (JSON) column of its parent's table, holding the array of child objects exactly as MappingEngine.buildOutbound already builds them for a normal outbound send.

The mapping input table is required (it is not needed for an ordinary outbound send): it names the target table, upper-cased and sanitized to [A-Z_][A-Z0-9_]*. It may be schema-qualified (DB.SCHEMA.TABLE or SCHEMA.TABLE) — only the last dot-separated segment is used as the (sanitized) table name, but giving the fully qualified name keeps the mapping's declared lineage (OpenLineageEmitter/connectors_lineage_declare, § 3.7) pointed at the same catalog asset that a publication run creates, instead of a second, junk asset under the connector's own default schema (OpenLineageEmitter.datasetOf only ever prefixes an unqualified table input with that default schema). If the qualified input names a schema different from the publication's own schema request field, the publication fails with an error naming both — there is no silent retargeting to the input's schema. Every rule and active child of the mapping becomes a column: a scalar rule (target with no . or []) becomes a column named after the target; a rule targeting a nested path becomes one JSON column named after its first path segment (several rules under the same segment merge into that one column); a child mapping becomes one JSON column named after its collectionPath. Four technical columns are appended to every table: _EBX_KEY (the record's formatted primary key — the business key when the table has one, key=true when it does not), _RUN_ID, _PUBLISHED_AT, _CONTRACT_VERSION.

Golden records and crosswalk. On a table under Match and Merge (ebx-addon-mame, configured independently of this module), the losing side of a merge (state MERGED) and logically deleted records (state DELETED) would otherwise be published next to the golden records, with nothing telling a consumer which transaction key belongs to which golden record. The mapping input mergedRecords (exclude, the default, or include; any other value fails the publication before anything is written) controls this per table: exclude leaves MERGED/DELETED records out — skipped records never count towards max — include keeps everything. Setting the mapping input crosswalk to true switches the default to include (a key/cross-reference table is meant to carry the merged records, resolved). Two transformations pair with crosswalk: golden(tablePath[,dataspace,dataset]) takes a record's formatted primary key and resolves it to its golden record's key when the record is MERGED (unchanged when the record is not found, the table is not under Match and Merge, or its state is not MERGED); mdmState(tablePath[,dataspace,dataset]) returns that record's consolidation state. A publication that excludes merged records still counts them in the report: tables[].skipped.merged / .deleted, and a successful run's message mentions the total when it is greater than zero. Typical shape — a key table publishing every record (merged included) resolved to its golden record, and a source-system cross-reference re-pointed the same way:

# key table: every record, merged ones included, resolved to its golden record
root mapping on /root/Companies, inputs {table: COMPANY_KEYS, crosswalk: true}
  ./Identification/Id -> ID
  ./Identification/Id -> GOLDEN_ID   golden('/root/Companies')
  ./Identification/Id -> MDM_STATE   mdmState('/root/Companies')
# source-system cross-reference, re-pointed to the golden record
root mapping on /root/CrossRefCompanies, inputs {table: COMPANY_XREF}
  ./source          -> SOURCE_SYSTEM
  ./pkRecordSource  -> SOURCE_KEY
  ./company         -> COMPANY_ID    golden('/root/Companies')
  ./company         -> ORIGINAL_COMPANY_ID

A consumer never joins on a merged (dead) key again: JOIN COMPANY_XREF x ON x.SOURCE_SYSTEM='ERP' AND x.SOURCE_KEY=t.CUSTOMER_ID JOIN COMPANY_360 c ON c.ID=x.COMPANY_ID. COMPANY_KEYS/COMPANY_XREF legitimately publish the matched table a second time (the key table is not counted as covering it, port-coverage-wise, by the data catalog's own rules).

The Publication table (dataspace/dataset Connectors, /root/Publication) keeps one row per connectors_publish call, dry runs included: runId (its primary key), product, contractVersion, connector, schema, status (OK, ERROR, DRY_RUN), message, cutoff, startedAt, endedAt, rowCount, mappings (CSV of the ids published), tables (CSV of TABLE=rows) and report — the full report below, as JSON text (osd:text, cut at 100000 characters). It is the durable record of a publication; a caller that only got back a runId (e.g. the workflow bean, whose message output is cut at 180 characters like every workflow variable, § 12.3) reads the full report back from this row.

sample (the first 3 documents per table) and plan (the statements that would run) are present only on a dry run (dryRun=true: nothing is executed, everything else in the report — table/column derivation, row counts, truncated — is computed exactly as a real run would). max bounds the rows read per table: by default (0 or absent) every row is published, read from EBX and loaded into the staging table in batches, so memory holds one batch whatever the table's size (audit C-17). A positive max, or the operator ceiling -Debx.connectors.publish.maxRowsPerTable, cuts each table there: the cut set still replaces the target tables atomically, but the run ends with status PARTIAL (never OK), truncated=true on the report and on the cut table, and a message saying so; the workflow step failOnError=true fails on PARTIAL too. recreate=true lets a target table whose columns differ from the contract be replaced (CREATE OR REPLACE TABLE) instead of the publication failing with the missing/ extra column names. A table's skipped object is present only when mergedRecords=exclude (the default) actually left records out (merged and/or deleted greater than zero); the top-level message of a successful run (real or dry) mentions the total across every table when it is positive.

The atomic commit and its limits. prepare creates the schema, the control table (EBX_PUBLICATION) and, per target table, the table itself and an empty staging table; load fills each staging table in batches (connector property publish.batchSize, default 500); commit is one single request running BEGIN … one DELETE+INSERT … SELECT * pair per target table (from its staging table) … an insert into EBX_PUBLICATION … COMMIT — either every table lands together or none does. EBX_PUBLICATION.PUBLISHED_AT is written with SYSDATE(), which is always UTC, into a TIMESTAMP_NTZ column — never CURRENT_TIMESTAMP(), which stores the Snowflake session's own time zone with no offset, so it silently reads back as if it were UTC (e.g. 09:06 Los Angeles for an 18:06 CEST cut-off). cleanup (staging tables dropped) runs after a successful commit and after any failure, best effort, never masking the outcome. This is deliberately narrow, and the extension points are left visible rather than hidden: full reload only, no incremental/upsert publication of a product (§ 10.1's deltas remain the way to keep a single mapping's target continuously in sync); no snapshot isolation of the source read (the records are read table by table, not against one consistent EBX dataspace snapshot, so a concurrent write during a long publication can be reflected in one table's cut and not another's); Snowflake only (TablePublisher, § 3.3.1, is the extension point for a second platform); no GRANTs and no dataspace-snapshot semantics are managed by this feature.

Describing and listing the published tables. After the commit, and best effort (a refusal by Snowflake is a warnings entry in the report, never an error on a committed publication), the publisher puts a comment on each table and column and sets the tags EBX_PRODUCT, EBX_CONTRACT_VERSION, EBX_SOURCE_TABLE and, when the request carries them, EBX_OWNER and EBX_DOMAIN (request fields description, owner, domain, title). With the connector property listing.enabled set to true it also shares the schema (EBX_<PRODUCT>_SHARE) and creates, or updates in place, an organizational listing EBX_<PRODUCT> visible to every account of the organization in the Internal Marketplace. That needs CREATE SHARE and CREATE ORGANIZATION LISTING on the account and a database owned by the connector's role. Properties: listing.enabled (default false), listing.supportContact (an e-mail address, required when listing is enabled) and listing.region (optional, default the account's region).

What each column means, and where to find it in Snowflake. When a column carries a meaning (label and description from the EBX model, business name, glossary term, definition and synonyms from the data catalog), its comment puts that meaning first (Customer name: … | Also called: … | Glossary term: … | ON EBX field ./name) and the column gets the tags EBX_GLOSSARY_TERM, EBX_SENSITIVITY and EBX_CLASSIFICATION. The publisher also writes, in the publication schema, a semantic view EBX_<PRODUCT>_SEMANTIC (CREATE OR REPLACE SEMANTIC VIEW, replaced at each publication): one logical table per published table, one dimension per business column with its glossary synonyms (WITH SYNONYMS) and its meaning as comment (business name and definition only), the key columns as PRIMARY KEY, one RECORD_COUNT metric per table, no relationship. It is what Cortex Analyst reads to answer questions in business words. Property semanticView.enabled (default true); it needs CREATE SEMANTIC VIEW on the schema. In Snowsight: comments in the table's Columns tab, tags via TAG_REFERENCES_ALL_COLUMNS('<DB>.<SCHEMA>.<TABLE>', 'table'), the view under the schema's Semantic views (SHOW SEMANTIC VIEWS IN SCHEMA, DESCRIBE SEMANTIC VIEW). Tables scanned by the catalog are read only: nothing is ever written back to them.

12. Running

12.1 User service (user interface)

On the table view of a table that has mappings: Synchronise with an external application. Options: mapping, scope (selection, view, whole table), maximum, simulation. The report details every record.

What the screen shows around a run:

  • before: when it was opened from a link with run-time inputs, a yellow banner says that nothing has run yet;
  • during: a click on Run reveals an animated strip with "Running…" (a simulation, and a run on the records of a table, are synchronous; the strip is the one of the material federated search, not a modal, and a 2-minute timer clears it if EBX refuses the form). A feed run for real is different: it starts on a background thread (below) and the screen answers at once with the live run panel;
  • after: a banner at the top, "Run finished at HH:MM:SS" (or "Simulation finished"), with the counts — green, red when an item failed, blue for a simulation;
  • Back: opened on a full ebx-ui page (the catalog's links), EBX renders no Close button; Back returns to the page the link was clicked on (the data catalog keeps it in sessionStorage, under a key that includes your EBX login), else one step back in the history. It hides itself wherever EBX draws its own Close.

Run mode, confirmation and details. The screen opens on a Run mode choice under the flow tiles: two cards, Simulate (blue, nothing is written or sent) and Run for real (amber), keyboard-operable as a radio group; simulation stays the default. The bottom button follows the mode (Simulate / Run and write, amber for a real run). The mode travels in the hidden request parameter ftcsMode. After a simulation, a banner gives the number of planned changes and an Apply these changes button that reruns the same options for real. A real run on the whole table of a records mapping does not start at once: a panel gives the record count (and the maximum when lower) with Confirm, Simulate first and Cancel. The check is made on the server (parameter ftcsConfirm = <mappingId>|ALL), so another mapping chosen afterwards asks again. The result tiles count simulated changes (DRY_RUN) as Changes planned. The details list shows errors first and only 20 rows. The next 20 come from the server through an EBX Ajax callback, on Show 20 more or when that button scrolls into view. Status filters (errors, updated, unchanged, no data, skipped) are applied on the server. A page asked by the screen of an older run is refused ("run again"). The progress strip shows the elapsed time.

Guided layout. When the service opens with run-time inputs on an import feed (the catalog's Re-profile this table…), it keeps to what matters: the title names the flow and the inputs ("Catalog profile: EBX_TEST · Companies/Companies/root/Companies"), a card says which connector and operation run, into which table, for which inputs; only the run mode cards are visible; the mapping and the maximum are folded under Advanced options (the scope, which a feed ignores, is not shown); the maximum is preset to 499; the item list is folded under Details (N items), open only when an item failed, with short item names (Identification/Id rather than the key predicate) and translated statuses. Opened from a table's toolbar, the screen keeps its full layout.

When a run fails. The screen does not show the raw exception. For the frequent failures it says what happened and what to do next, in the language of the user's EBX session, then folds the technical detail (the redacted message, never a stack trace) under Technical detail: connection refused, host that does not resolve, timeout, credentials or rights refused, rate limit, a private or non-allowed address (with the property an administrator sets: ebx.connectors.egress.privateExceptions, ebx.connectors.allowedHosts), a secret stored in clear text (ebx.connectors.secrets.allowClear), a mapping already running, too many background runs, an invalid mapping. Any other failure says "The operation failed" and shows the technical detail open; the full trace is in the kernel log. The same cause and action appear under a failed row of the details and in the result of Test connection (core/ErrorCatalog classifies; the sentences are the error.* keys of the UI bundles, fixed text: a secret or a record value quoted by the remote system never reaches them).

A feed run from the screen is an explicit run, as on POST /sync: its lineage leaves in one OpenLineage event when it ends. Without it every imported item sent its own event, and the catalog imported each one separately (a 58-column profile took 30 s in the screen against 4.6 s over REST, 2026-09-14).

Three optional URL parameters, declared as input parameters of the service, prefill it: mapping=<id> (the mapping selected), inputs=<name=value;…> (run-time inputs of a feed, § 5, shown above the report) and dryRun=false (opens on Run for real once; the run still needs a click on Run). The data catalog's Re-profile this table button opens the service this way on its profile flow.

How to pass them. The ebx-ui routes (/ebx-ui/ui/advanced/…, /ebx-ui/ui-node/…) ignore plain query parameters of a service — …?service=ebx-connectors@ConnectorSync&serviceMode=TABLE_VIEW&mapping=159 opens the default mapping (measured 2026-09-14). Two forms work:

  • a web component URL, which EBX redirects: /ebx/?branch=<dataspace>&instance=<dataset>&xpath=<table path>&service=ebx-connectors@ConnectorSync&mapping=123&inputs=tables%3DSALES.ORDERS&dryRun=false;
  • the ebx-ui route with serviceParams, the base64 of a JSON object (what the catalog button builds): /ebx-ui/ui-node/data/B<dataspace>/<dataset><table path>?service=ebx-connectors@ConnectorSync&serviceMode=TABLE_VIEW&serviceParams=<base64 of {"mapping":"123","inputs":"tables=SALES.ORDERS","dryRun":"false"}>.

The presets are read when the service opens; EBX then rewrites the address keeping only mapping, so a reload of the page loses the run-time inputs — the banner that lists them disappears with them. The maximum counts imported items (one per column for a catalog profile). It has no upper bound on the form: a feed run for real starts in the background and has none; a simulation, or a run on records, holds its items in the HTTP request and is refused above 4,999 with a message that says why. Each feed starts at 499.

Live run panel (feed runs for real). Run and write on an inbound feed no longer runs inside the HTTP request. The screen starts the run through the same path as connectors_sync(async=true) and POST /sync?async=true, so it has the same admission limits (-Debx.connectors.import.async.maxConcurrent and maxQueued, one run per mapping at a time) and returns at once with a Run in the background panel under the result area:

  • the state in words (Running, Finished, Finished with errors, Failed, Stopped, Interrupted), an animated bar while it runs, and tiles for the items processed, created, updated, unchanged, skipped, the errors and the elapsed time (the counters are those of the last saved batch, read from the same run status as connectors_run_get; the panel polls every two seconds and stops polling when the run ends);
  • Stop (the RUN right) asks the run to stop at its next batch boundary; it keeps its position;
  • Resume from item N appears for a stopped, interrupted or failed run that saved a position, when the screen started the run itself: it starts a new background run at that item (the source must return its items in the same order as before, as for resumeFrom over MCP and REST);
  • Refresh, and links to the log rows of the run and to its failures;
  • a failure is told as a cause and a next action (see below), a run cut at its maximum says how many items the source had.

You may leave the screen: the run continues. Reopening the screen on a mapping whose feed is already running (started from any entry point of this node) shows the same panel, with Stop. A reader with the READ right only watches; Stop and Resume need RUN, which the screen itself requires. The record form of an ExecutionRun row shows the same panel, with Refresh and Stop but no Resume.

12.3 Workflow

Bean com.on.ebx.connect.ebx.workflow.ConnectorScriptTaskBean (module ebx-connectors), or the ready-made model ConnectorEnrichment. Inputs: dataspace, dataset, xpath (one record) or tablePath + predicate + maxRecords (a table), mappings (ordered list, recommended form) or connectors or connector/operation/direction, dryRun, failOnError, inputs (run-time inputs of the feeds among the mappings, § 5). Outputs: report, changedCount, okCount, errorCount, status (OK, PARTIAL, ERROR, NO_DATA), conflictCount, hasConflicts, runId (input scope for outbound deltas, § 10.1) (true/false, to route to the "Manage connector conflicts" user task, § 4.5), truncated, problems and warnings (the run-time inputs no mapping of the step read, § 5; empty when none). The step does not fail by default (failOnError=false): the workflow routes on the outputs. truncated is true when a feed or the table held more than maxRecords, so the step did not process everything; problems lists what keeps the run from being a plain success (errors, rejected, conflicts, truncated, stopped, comma-separated) and is empty for a clean run. A feed whose call to the source failed counts as one error. Launch example through MCP: publication ConnectorEnrichment, parameters xpath=/root/Companies[./Identification/Id=512], mappings=37,38,1,42,44.

In the workflow editor, declare the step as a library script task and pick the bean in the list of module ebx-connectors (key ebx-connectors@com.on.ebx.connect.ebx.workflow.ConnectorScriptTaskBean): this is what shows its input and output parameters in the step form, where each one is mapped to a data context variable (mappings = ${mappings}, xpath = ${xpath}...); those variables, declared as in, are then asked at launch. A "specific" script task typed with the bare class name runs just as well, but the editor shows no parameter form for it.

Publishing a data product (§ 10.2) is a separate bean, declared the same way: key ebx-connectors@com.on.ebx.connect.ebx.workflow.ProductPublishTaskBean. Inputs: mappings (ids or labels, comma-separated, all on the same connector), schema, product, contractVersion (default 1), dryRun, recreate, maxRecords (default 0 = every row), failOnError (default true, unlike ConnectorScriptTaskBean's false: a publication is meant to succeed as a whole, so the step goes in error by default when the report is ERROR). Outputs: runId, status (OK, ERROR, DRY_RUN), message (cut at 180 characters like every workflow variable), rowCount. The full report is never passed as a variable — read it back from the Publication table by runId (§ 10.2).

12.4 Scheduled task

Class com.on.ebx.connect.ebx.scheduler.ConnectorScheduledTask, parameters connector, operation, direction, dataspace, dataset, tablePath, predicate, maxRecords (100), dryRun, scope, inputs (run-time inputs of a feed, § 5). Example: every night, GLEIF / lei on /root/Companies with the predicate ./Identification/LegalEntityIdentifier != '' and ./Governance/gleifLastUpdate = ''.

The mapping is found from (connector, operation, direction, tablePath); when two mappings match, the task refuses to run. For a feed, maxRecords is the number of items imported, not of records of the table: a data catalog profile imports one item per column, so a nightly profile of a catalog source takes connector=<its connector>, operation=profile, dataspace=DataCatalog, dataset=DataCatalog, tablePath=/root/ProfileSnapshot, maxRecords=10000 (catalog guide §3.15 lists the other catalog flows).

A scheduled execution fails when its run is not a plain success. Nobody watches a scheduled run, so the execution is reported failed in the task scheduler (what was written stays written) when the run ends with items or records in error, a source that could not be read, rejected items, conflicts left for a steward, a read cut at maxRecords, or a run stopped before its end. The message names the cause and, for a cut read, the parameter to raise: the default maxRecords of 100 is a safety bound, not a recommendation - set it above what the source holds. A record for which the source had no data is not a failure, and neither is a table enrichment with a predicate that reaches maxRecords (a nightly run over "what is not enriched yet" drains its backlog a hundred records at a time; the execution information says that more records match). Without a predicate the same situation is a cut read: the next execution would start again from the same first records. To accept some causes for a given task, set its tolerate parameter to a list among errors, rejected, conflicts, truncated, stopped, or to all (for instance tolerate=conflicts for a feed whose TRUSTED rules routinely leave proposals to a steward); a tolerated cause is still written in the execution information.

12.7 MCP tools (agents)

The module exposes its features as MCP tools (Model Context Protocol), so that an agent such as Claude Code can discover connectors, run enrichments, arbitrate conflicts or move a configuration. The 23 tools: connectors_help, connectors_list, connectors_describe, connectors_call, connectors_mappings_list, connectors_mapping_get, connectors_mapping_upsert, connectors_mapping_delete, connectors_enrich, connectors_sync, connectors_replay, connectors_run_get, connectors_outbound_states, connectors_conflicts_list, connectors_conflict_decide, connectors_log_search, connectors_config_export, connectors_config_import, connectors_openapi_import, connectors_lineage_declare, connectors_publish, connectors_run_stop (stop a running import or asynchronous send) and connectors_catalog_source (how the data catalog knows the system a connector reaches). They run in the caller's EBX session, so EBX permissions apply; secrets never transit through them.

connectors_mapping_upsert writes a whole mapping, sub-object mappings included: a child that omits connector, operation, direction, dataspace or dataset takes them from its parent. An import feed (§ 9) sets keyPredicate, itemsPath and createIfMissing, flat or under feed {}; a feed without keyPredicate is reported in notes. connectors_sync on a feed, without key, predicate or scope, runs the feed like POST /sync/{id} (optional inputs as JSON text; dryRun=true lists the values without writing, Kafka messages peeked, not committed). connectors_publish sends one or more root outbound mappings as a whole product, one atomic commit for every target table (§ 10.2); mappings is a comma-separated list of ids or labels, all on the same connector.

Two ways to reach them, both on by default (-Debx.connectors.mcp=native|endpoint|both|none):

  • Native MCP runtime of EBX 6.3: at module registration, the server ebx-connectors is declared through the public API (registerMcpServer and the @McpServer / @McpTool annotations, the same API as the built-in workflow and data-access servers) and served by EBX at /ebx-assistant/mcp/v1/ebx-connectors, with the activation and permissions of the MCP administration. The call is made by reflection: on an older EBX the runtime is simply absent, and the kernel log says so. In the 6.3 development builds seen so far EBX only accepts core and add-on modules; the log then says "EBX declined the MCP server registration" and the endpoint below serves.
  • The module's own endpoint, POST /ebx-connectors/rest/mcp: MCP over streamable HTTP (JSON-RPC 2.0, JSON answers, no server-sent events; GET and DELETE answer 405 with Allow: POST,OPTIONS, which is what makes MCP clients fall back to plain request/response), authenticated like any EBX REST call (HTTP Basic, token, session). Works on every EBX version that runs the module. Configure an MCP client with {"type": "http", "url": "http://host:8080/ebx-connectors/rest/mcp", "headers": {"Authorization": "Basic ..."}}.

GET /ebx-connectors/rest/v1/config and POST /config?dryRun=true are the REST twins of the export/import tools: connectors matched by id, mappings by connector, operation, direction, table and label, rules and inputs replaced, secrets never exported nor overwritten.

13. Log and statuses

Every call writes a SyncLog row: timestamp, connector, operation, direction, table, record, status, message, duration, origin (user service, workflow admin, REST admin, scheduler, trigger, webhook …).

Status Meaning
OK at least one change written
NO_CHANGE call succeeded, nothing to write (already set, IF_EMPTY policy)
NO_DATA the service returned nothing for these inputs (no LEI, address out of scope)
SKIPPED a required input is empty on the record, or no applicable mapping
ERROR the service or the mapping failed (message = the cause: missing key, MS_MAX_CONCURRENT_REQ, unknown transformation…)
DRY_RUN simulation: changes computed, not written

Health metrics. One row per connection in Connector health and metrics, updated after every execution: the counters are records, not log lines. A feed run in batches writes one SyncLog line per batch (1,000 items by default) plus an own line for each failing or conflicting record; the metrics read the tally of the batch line, so a batch of 1,000 records counts 1,000 records (inbound), its unchanged and rejected ones as records without change and its conflicts as conflicts, and the own lines of its failing records are not counted a second time. The latency percentiles take the time per record of a batch. A failure for the Reliability rule (one failure in a row: degraded, three: failed) is a failed call or record, or a batch in which every attempted write failed; a batch with some failed records is not a failed batch (its failures are in its counts, in the run status and in their own log lines). The repeated-failure alert follows the same rule.

14.7 AI-assisted classification with a human in the loop

The Claude connector (type llm, trust 30) classifies a company from its description:

  • input text = ${./Identification/description}, input categories = the NACE sections (A=Agriculture;B=Mining;C=Manufacturing;... or a constant taken from a reference table);
  • rules: category → ./AdditionalInformation/naceCode with fk(/root/ReferenceData/NaceCode), policy TRUSTED; reason → a comment field if the model has one.

14.8 Documents, DAMA assets and images

The documents connector (category AI) turns unstructured documents into record values. It reads the text of a PDF (text layer), DOCX, text, Markdown, CSV or HTML document, asks an llm connector (property llm.connector) for the attributes listed in fields, and returns one item per document. Each value comes with a confidence and the words of the document that state it; the module checks those words against the text. A normal inbound mapping imports the item: a value at or above confidence.threshold (0.8) is written, with its source kept in FieldProvenance.source; a value below it becomes a proposal in the conflict manager. A model's confidence never goes above 0.99, so threshold 1 sends every value to a steward.

Where the document comes from:

  • an upload on the connector row, a content input (base64 with name), or a file of the server folder folder (only under -Debx.connectors.documents.roots);
  • a DAMA asset (EBX Digital Asset Manager): input record (the record whose media field holds the document) or asset (its UUID), with the table and field from the dama.* properties. It is read with the caller's session: the record must be visible and the field not hidden, and DAMA applies its own rights.

A mapping on extract with input record = ${./id} fills the record's own fields from the document it holds. Start it from a workflow (ConnectorScriptTaskBean) or from ConnectorTableTrigger with watchedFields = ./document: the trigger runs after the save, in the background, by default.

The annotate operation (write) puts the extracted metadata on the DAMA asset itself (metadata = attribute:CODE, only metadata types entered by hand, IF_EMPTY by default). It chooses tags (tags = true or max:N) only from DAMA's existing tags, never created, and adds them to a list field of the record that holds the document, named by dama.tags.field (for example ./documentTags): DAMA's public API cannot tag an existing asset, and the module does not write DAMA's own tables. The write uses the caller's session and needs that field read-write. Without dama.tags.field, the tags are only returned. Below the threshold, metadata wait in the conflict manager as document (DAMA metadata): CODE proposals, and tags as ordinary proposals on the tags field; accepting one adds that tag to the list.

Images and scanned PDFs. With vision = true on the documents connector and on the llm connector (whose model must accept images), an image (png, jpeg, gif, webp, up to max.image.bytes, 5 MB) or a PDF without text layer (up to max.pages, 20) is sent to the model itself. Nothing can check what the model reads in an image, so its values are capped at vision.confidence.max (0.7, below the threshold): by default a steward confirms them. PDFs are read by Anthropic, OpenAI, Google and Mistral models; Azure and Ollama take images only. The image leaves EBX for the provider: see § 3.1.2.

Reference: DOCUMENTS.md, DAMA-DOCUMENTS.md and DOCUMENTS-VISION.md in the module's docs folder.

15. Cheat sheet for an AI agent

Decision procedure to enrich a record:

  1. GET /ebx-connectors/rest/v1/connectors: which connectors have their secrets (configured).
  2. GET /ebx-connectors/rest/v1/mappings?table=<table>: which inbound mappings exist, active, not feeds, not children.
  3. Order them: first those that produce an identifier (search by SIREN / name), then those that consume it (record by LEI), then the complements (addresses, sanctions).
  4. POST /enrich?dataset=&table=&key=&mappings=<list>&dryRun=true, read results[].status and changes, then run again without dryRun.
  5. SKIPPED = empty input (complete the data or pick another mapping); NO_DATA = the service does not know the entity; ERROR = read message.
  6. hasConflicts true: GET /conflicts?dataset=&table=&key= shows what a less trusted source proposed; never overwrite silently, decide with POST /conflicts/{id}/accept|reject (or leave it to a steward).

17. Connector type catalogue

Kinds: R = read, S = search, W = write. The inputs of every operation are listed by GET /connectors and in the designer (Service call panel).

The catalogue is the runtime contract, not a promise that every connector is configured. A connector is usable only when it is active, its required secret or identity is configured, its optional driver is available, and its configuration passes validation. Use the catalog or GET /connectors to discover availability, then use Test connection or Preview before a write. A preview, dryRun=true, or a non-destructive peek is the preferred evidence step; receive, consume, complete, and every W operation can change an external system or message state.

Dedicated database types share the parameterized JDBC engine: use prepared inputs, bounded max.rows, and a JNDI DataSource where operations manage the connection. Dedicated messaging types are deliberately bounded and distinguish a non-destructive peek from consuming/acknowledging a message. Types loaded through an optional library (Kafka, SFTP, AMQP/JMS providers, JDBC drivers and the Azure Service Bus SDK) appear only when that library is present; the rest of the catalog remains available.

Stored procedures through JDBC

The JDBC family exposes the write operation procedure. Supply either procedure, a safe one-to-three-part identifier such as governed.enrich_company, or call, a single JDBC escape such as {call governed.enrich_company(?,?)}. An explicit call accepts only the identifier and ? placeholders: literals, comments, semicolons and multiple statements are refused. parameters is a JSON array (maximum 64 entries) whose items contain a unique name, mode (IN, OUT, INOUT, or first-position RETURN), and a bounded JDBC type: VARCHAR, INTEGER, BIGINT, DECIMAL, BOOLEAN, DATE, TIME, TIMESTAMP, or VARBINARY (documented aliases are accepted). IN values are read by name from the outbound document, then operation inputs. Results contain affectedRows or one bounded result, plus out; each OUT value is limited to 64 KiB. The connector commits a successful call and rolls back an error, but a procedure can have external or non-transactional effects. Driver-specific named arguments, REF CURSOR, structured/LOB parameters, multiple result sets and default arguments are not part of this portable contract. Grant EXECUTE only on an approved allow-list of procedures and treat every invocation as a live write.
